# Comprehensive Color System Implementation & Deployment Workflow

This workflow combines all the components needed to set up, deploy, and manage your Color System environment across different platforms and deployment options.

## 1. Color System Overview

The Color System is a comprehensive environment that includes services, local implementations, Docker containers, cloud deployments, and orchestration tools. It provides color-based feedback in terminal applications with standardized roles (warning, error, success, info, etc.) and allows for consistent styling across environments.

### Core Components


- **Services**: Includes governor.service (master orchestration), security.service (Security Enforcement Agent), watchdog.service (resource monitoring), and postgresql.service.
- **Color Roles System**: A standardized schema mapping roles like "warning", "success", "error" to specific colors.
- **Aliases**: Shell shortcuts like `cwarn`, `csuccess`, `cerror`, and `creset` for quick styling.


## 2. Setup & Installation Workflow

### Step 1: Local Environment Setup


1. Clone the repository:
   ```bash
   git clone https://github.com/peteywee/color-system.git
   cd color-system
   ```

2. Run the bootstrap script:
   ```bash
   chmod +x bootstrap/bootstrap.sh
   ./bootstrap/bootstrap.sh
   ```

3. Verify installation with color tests:
   ```bash
   source ~/.bashrc
   cwarn "This text should be yellow"
   cerror "This text should be red"
   csuccess "This text should be green"
   creset
   ```

4. Register systemd services:
   ```bash
   sudo cp security/security.service /etc/systemd/system/
   sudo cp governor.service /etc/systemd/system/
   sudo systemctl daemon-reload
   sudo systemctl enable governor.service security.service
   sudo systemctl start governor.service security.service
   ```


### Step 2: Configure Environment Files


Create your environment by copying the example file:
```bash
cp .env.example .env
nano .env
```

Example contents:
```
GIT_USER="peteywee"
GIT_EMAIL="your.email@example.com"
SUPABASE_PROJECT="your-project-id"
VERCEL_TOKEN="your-vercel-token"
```

### Step 4: Automate GitHub Pages Deployment


Create a GitHub Actions workflow for automated deployment. Add this file as `.github/workflows/deploy-pages.yml`:

```yaml
name: Deploy GitHub Pages

on:
  push:
    branches:
      - main

jobs:
  build-deploy:
    runs-on: ubuntu-latest
    permissions:
      pages: write
      id-token: write

    steps:
      - name: Checkout repository
        uses: actions/checkout@v3

      - name: Setup Ruby
        uses: ruby/setup-ruby@v1
        with:
          ruby-version: '3.x'

      - name: Install dependencies
        run: |
          gem install bundler
          bundle install

      - name: Build site with Jekyll
        run: |
          bundle exec jekyll build --destination _site

      - name: Upload artifact for Pages
        uses: actions/upload-pages-artifact@v1
        with:
          path: _site

      - name: Deploy to GitHub Pages
        uses: actions/deploy-pages@v1
```


## 4. Docker Implementation

### Step 5: Docker Container Setup


1. Create a Dockerfile with fallback support:
   ```dockerfile
   ARG BASE_IMAGE=debian:trixie
   FROM ${BASE_IMAGE}

   # Install essential packages
   RUN apt-get update && apt-get install -y \
       curl wget git jq bash sudo \
       nodejs npm \
       && rm -rf /var/lib/apt/lists/*

   # Copy project files
   COPY . /opt/project
   WORKDIR /opt/project

   # Run bootstrap with error handling
   RUN chmod +x bootstrap/bootstrap.sh \
       && ./bootstrap/bootstrap.sh || \
       { echo "Trixie build failed, using Bookworm"; exit 1; }

   # Default command
   CMD ["/bin/bash"]
   ```

2. Create a fallback build script:
   ```bash
   #!/usr/bin/env bash
   # Location: build-with-fallback.sh

   echo "[+] Attempting to build with Debian Trixie..."
   docker build --build-arg BASE_IMAGE=debian:trixie -t color-bootstrap-trixie . && {
     echo "[✓] Trixie build succeeded."
     exit 0
   }

   echo "[!] Trixie build failed. Falling back to Bookworm..."
   docker build --build-arg BASE_IMAGE=debian:bookworm -t color-bootstrap-bookworm .
   ```

3. Set up Docker Compose:
   ```yaml
   # Location: docker-compose.yml
   version: '3.8'
   
   services:
     color-system:
       build:
         context: .
         args:
           BASE_IMAGE: debian:trixie
       volumes:
         - ./data:/opt/project/data
       environment:
         - GIT_USER=${GIT_USER}
         - GIT_EMAIL=${GIT_EMAIL}
       restart: unless-stopped
   ```


### Step 6: Docker Usage


1. Build with fallback logic:
   ```bash
   chmod +x build-with-fallback.sh
   ./build-with-fallback.sh
   ```

2. Run using Docker Compose:
   ```bash
   docker-compose up -d
   ```

3. Access the container:
   ```bash
   docker exec -it color-system_color-system_1 bash
   ```

4. Use color system inside container:
   ```bash
   cwarn "Warning message"
   csuccess "Success message"
   ```

2. Set up the droplet:

   ```bash
   git clone https://github.com/peteywee/color-system.git

   # Run the bootstrap script
   chmod +x bootstrap/bootstrap.sh

   cp security/security.service /etc/systemd/system/
   cp governor.service /etc/systemd/system/

   systemctl start governor.service security.service
   ```

### Step 8: Cost Optimization for Cloud


If using GitHub Education Pack ($200 credit for 12 months):

1. Start with smallest viable droplet (1GB RAM, $4/month)

2. Add swap space for memory:
   ```bash
   sudo fallocate -l 1G /swapfile
   sudo chmod 600 /swapfile
   sudo mkswap /swapfile
   sudo swapon /swapfile
   echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
   ```

3. Implement scheduled shutdowns during inactive periods:
   ```bash
   # Add cron job to shut down at 2 AM
   echo "0 2 * * * /sbin/shutdown -h now" | sudo tee -a /etc/crontab
   ```

4. Create snapshots instead of keeping droplets running when not in use

## 7. Security Considerations

### Step 12: Security Implementation


The Security Enforcement Agent (SEA) provides:
- File permission hardening
- Cron job backdoor detection
- Sudoers configuration validation
- Sensitive file monitoring
- Bash history sanitization
- Intrusion detection and alerting


### Step 13: Security Validation


```bash
# Check SEA agent status
systemctl status security.service

# Manually run security check
./security/sea_agent.sh --scan

# View security logs
cat $HOME/.assistant/security/sea_*.log

# Test file permission enforcement
```

### Step 14: Critical Security Precautions


Important security notes:
- Never expose .env file with sensitive tokens
- Periodically review security logs
- Run monthly security audits:
  ```bash
  ./security/sea_agent.sh --audit > security_audit.txt
  ```

- Ensure SSH keys are properly protected (600 permissions)


## 8. Maintenance & Troubleshooting

### Step 15: Automated Maintenance


Create a watchdog script for automated maintenance:

```bash
#!/usr/bin/env bash
#
# watchdog.sh — keep Color Role System healthy & up-to-date
#
set -euo pipefail

REPO="TopShelfServiceLLC/color-system"     # ← change if you fork
INSTALL_DIR="${HOME}/.color_system"
LOG_FILE="${INSTALL_DIR}/update.log"

# --- helper ---------------------------------------------------------------
timestamp() { date '+%Y-%m-%d %H:%M:%S'; }

log() { printf '[%s] %s\n' "$(timestamp)" "$*" >> "$LOG_FILE"; }

fatal() { log "ERROR: $*"; exit 1; }

current_ver() {
  grep -m1 '^# Version:' "$INSTALL_DIR"/loader.sh | awk '{print $3}'
}

latest_ver() {
  curl -sSL "https://api.github.com/repos/${REPO}/releases/latest" \
    | jq -r '.tag_name'
}

install_version() {
  local ver="$1"
  log "Installing $ver ..."
  curl -sSL \
    "https://github.com/${REPO}/releases/download/${ver}/color-system-${ver}.tar.gz" \
    | tar xz -C "$INSTALL_DIR/.."

  cd "$INSTALL_DIR/../color-system-*"
  bash install_hook.sh --clean >> "$LOG_FILE" 2>&1
  log "Install complete."
}

# --- run --------------------------------------------------------------------
mkdir -p "$INSTALL_DIR"
touch "$LOG_FILE"

[[ -x "$(command -v jq)" ]] || fatal "jq not installed"

# 1. Sanity-check core files
for f in loader.sh aliases.sh color_roles.json; do
  [[ -f "${INSTALL_DIR}/${f}" ]] || fatal "Missing ${f}"
done

INSTALLED="$(current_ver || echo 'unknown')"
LATEST="$(latest_ver)"

if [[ "$LATEST" != "$INSTALLED" ]]; then
  log "Update needed: installed=${INSTALLED}, latest=${LATEST}"
  install_version "$LATEST"
else
  log "No update needed (version ${INSTALLED})"
fi
```

Set up a daily cron job:
```bash
crontab -e
# Add:
# Color Role System watchdog – runs daily at 03:30
30 3 * * *  ~/.color_system/watchdog.sh
```


### Step 16: Troubleshooting Common Issues


| Issue | Cause | Solution |
|-------|-------|----------|
| Colors not working in shell | colors.source.sh not loaded or jq missing | `source ~/.bashrc; sudo apt install jq` |
| Permission denied errors | Script not executable | `chmod +x path/to/script.sh` |
| Services not starting | Path issues or dependencies missing | `sudo systemctl status service-name; journalctl -u service-name` |
| GitHub authentication failing | Token expired or missing | `./tools/gh_setup.sh --refresh` |
| PostgreSQL connection issues | Service not running or auth problems | `sudo systemctl restart postgresql; ./tools/psql_shortcuts.sh --repair` |

### Step 19: Color Role System Reference


The color scheme supports these built-in roles:

| Role | Description | Default Color | Alias |

| error | Error messages | Red (#FF0000) | `cerror` |

| info | Informational text | Blue (#1E90FF) | `cinfo` |
| reset | Reset formatting | Default | `creset` |
