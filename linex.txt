# 1. Find latest release tarball URL
get_asset_url() {

    | grep browser_download_url \
    | cut -d '"' -f 4 \
    | grep "${ASSET_PATTERN}" \

download_and_unpack() {
  local url="$1"
  echo "🔽 Downloading ${url}"
  curl -sSL "$url" | tar xzv
}

run_hook() {

  cd color-system-*  
  bash install_hook.sh "$@"

  # Build the release asset URL once; triggers Terraform replacement if version changes
  asset_url = (
    var.custom_asset_url != "" ?
    var.custom_asset_url :
    "https://github.com/${var.github_repo}/releases/download/${var.tag}/color-system-${var.tag}.tar.gz"

  extract_parent = "${var.install_dir}/_src"

resource "null_resource" "install_color_system" {
  triggers = {
    asset_url   = local.asset_url
    install_dir = var.install_dir
  }

  provisioner "local-exec" {
    interpreter = ["/usr/bin/env", "bash", "-c"]

      set -euo pipefail

      echo "🔽  Fetching Color Role System from ${local.asset_url}"

Short answer
No – you do not need a separate Git repository for every Terraform “thing.”
What you actually need is a clearly-scoped root module directory for each independent deployment, plus one (or more) shared module directories or repos that those roots can call.

1 How Terraform’s files are scoped
Level	What it is	Lives where	Typical contents
Root module	A self-contained deployment you run with terraform init / plan / apply.	Any directory that contains *.tf files and no parent dir with TF files.	Provider blocks, main.tf, variables.tf, terraform.tfvars, outputs.tf, backend config.
Child/Shared module	Re-usable logic that a root (or another module) calls with source = "./modules/foo" or source = "github.com/org/foo//db"	Either:
• a modules/ folder inside the same repo, or
• a separate repo versioned on its own.	Only the resources for that module; no backend config.
The root module is the unit of state; each root produces exactly one terraform.tfstate file (local or remote). Child modules don’t hold state—roots do.

2 How to organise in Git & on disk
Option A Single-repo / mono-repo (common for personal or small shops)
infra/
├── main.tf               # root for “dev”
├── prod/                 # root for “prod”
│   └── main.tf
└── modules/
    ├── color_system/     # your new module
    └── vpc/
Pros – one remote, easy cross-module refactoring, single PR workflow.

Cons – any change triggers CI for the entire repo; release/versioning of modules is manual (you tag the whole repo).

Option B Root-repos + shared-module-repos (medium/large teams)
color-system/                 # Git repo A – reusable module

Your Crostini container’s root filesystem just flipped to read-only.
When that happens apt can’t create temp files, so every repository signature check fails and packages like terraform/terragrunt are “missing.”

Typical triggers:

I/O error on the underlying ext4 image → kernel remounts / as read-only.

Disk is completely full.

A power loss / Chromebook sleep glitch that left the container in an inconsistent state.

Until the filesystem is writable again, nothing that needs /tmp, /var/lib/apt, or dpkg locks will work.
